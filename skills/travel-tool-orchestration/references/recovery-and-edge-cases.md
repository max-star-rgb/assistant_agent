# 旅行编排恢复与边界

## 多目标依赖

- 先把住宿、严格距离、路线、天气等要求拆成独立目标，不把第一个成功结果当作整个请求完成。
- `lodging_search` 先提供日期报价和库存候选；步行或通勤硬约束再由路线工具核验。
- 天气通常不依赖住宿或路线结果，可以独立执行，但最终仍要与其他目标一起核验完整性。
- 某个目标失败时继续执行不依赖它的目标，最终分别说明已完成证据和受阻部分。

## 日期与地点

- 相对日期以 system prompt 中可信的本地时间和时区解析。存在两种常见解释且会改变住宿或天气结果时才澄清。
- 用户说“今晚住一晚”且地点时区明确时，可以把当地次日作为退房日并说明；用户明确表达其他晚数时以用户为准。
- 住宿人数或房间数未提供时按本轮 `lodging_search` ToolSpec 默认值查询，并在结果中说明；上下文表明是多人或多房需求时，缺失数量会实质改变结果，应先澄清。
- “每晚不超过 X”传入每晚最高预算。回答同时保留工具返回的 `nightly_price`、`total_price` 和 `price_basis` 口径，不自行断言含税、锁价或每晚价格完全相同。
- 用户未指定目标地点但运行时有明确当前位置时，可以使用该默认地点；标记为默认或粗粒度的位置不能伪装成用户精确位置。
- 用户明确要求“当前位置”或“附近”时，先检查本轮 ToolSpec：可信结构化上下文已提供必需 IP，或 ToolSpec 允许省略 IP 时，才调用 IP 定位。当前 ToolSpec 要求 IP 且上下文没有时，询问城市、区域或附近地标，不要求用户额外暴露原始 IP。

## 区域 POI 与路线

- “西湖”“市中心”“景区”等区域不是唯一坐标。优先根据用户上下文选择明确入口、车站或代表性 POI，并在答案中说明落点。
- 用户没有指定区域落点时，通过地点搜索选择与出发方向和交通方式匹配、工具结果可明确定位的代表性入口或交通节点；找不到唯一合理落点时先澄清，不凭常识虚构坐标。
- 公共交通集成路线可能包含公交、地铁、步行或换乘组合；只按工具实际返回的交通方式描述。路线 ToolSpec 没有出发时间字段时，结果只作为本次查询的规划参考，不声称是入住日某一时刻的精确耗时。
- 候选较多时，先按用户明确的预算、库存、排序和位置偏好缩小集合，再按住宿结果排序逐批核验。用户未指定推荐数量时，最终最多推荐 3 个；持续核验直到获得 3 个满足全部硬约束的候选、候选耗尽或触及本轮明确的工具预算。
- 因工具预算停止时必须说明已核验范围，不得声称未核验候选不满足约束；不能把其中一条路线结果推广到其他候选。
- 严格“步行 15 分钟内”按工具原始时长不超过 900 秒判断，不用四舍五入后的展示分钟放宽门槛；工具没有足够精度时明确无法严格核验。

## 空结果与失败恢复

- 辅助查询为空时最多进行一次有实质差异的修正，不连续替换“酒店、宾馆、住宿”等近义词。
- `maps_around_search` 为空只说明该中心、半径和关键词没有返回 POI；`lodging_search` 不依赖该结果时直接继续。
- 高德空结果不能证明住宿 Provider 没有候选，住宿 Provider 空结果也不能证明地图上不存在酒店 POI。
- Provider 失败或结果缺关键字段时，不补写价格、库存、距离、路线或天气；给出已获得的独立证据和具体限制。
- 天气结果未覆盖用户旅行日期时，把该天气目标标记为受阻，不使用相邻日期预报替代。

## 回答边界

- 高德酒店 POI 不代表指定日期可订，也不包含可靠房价和库存。
- `lodging_search` 的价格、库存和 OTA 候选不能替代路线证据。
- `nearby_poi` 不是距离或步行时间证明。
- 具体地点、价格、距离、库存、路线和天气事实只能来自本轮对应工具证据。
