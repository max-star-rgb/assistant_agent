# 示例：用户说“我想明天去桐庐漂流”

本示例只演示编排方式。日期、天气、开放状态、酒店、路线和餐厅均须在实际对话中查询，不得复用示例占位符。

理想顺序：

`解析“明天” → 最小澄清 → 可成行性门 → 漂流点选择 → 交通 → 住宿 → 景点 → 餐饮 → 最终方案`

角色边界：Planning coordinator 先读取本 Skill 和本 reference，把澄清顺序、停止条件和输出要求写进完整的
`task` description；它不激活 Tool Profile。执行 Agent 收到任务后，只有在首次需要酒店、地点或路线工具时才调用
`activate_tool_profile(profile_id="travel")`。加载 Skill 与激活 Profile 是两个独立动作；天气工具无需激活 Profile。

## 1. 首轮只补最小信息

先按用户时区把“明天”解析为绝对日期。日期已知，不再追问。

回复示例：

> 好的，我先确认 `<YYYY-MM-DD>` 是否适合漂流，再继续规划路线、酒店和吃饭。请告诉我从哪里出发、几个人、准备当天往返还是可以住一晚；如果有儿童、老人或行动不便的同行者，也请一起说明。

这轮只取得会影响可行性和第一批查询的硬约束，不一次询问交通、酒店、景点和餐饮偏好。

## 2. 先核验明天能不能漂

取得最小信息后：

1. 执行 Agent 激活 `travel` Tool Profile，再用 `mcp_amap_maps_maps_text_search` 识别桐庐实际漂流景区和明确入口；
   不能把“桐庐漂流”当成唯一 POI。
2. 直接用独立可见的 `mcp_amap_maps_maps_weather` 查询目标日期天气；结果不足时用 Provider-native 联网搜索核验
   权威气象来源。
3. 通过运营主体或官方来源核验开漂、预约、票务、临时关闭，以及年龄、身高等限制。

### 不可成行或风险过高

若天气、停运公告或同行者限制使核心活动不可行，立即停止酒店、详细路线、景点和餐饮查询。说明已核验依据，并只推进一个新决策：

> 明天暂不建议按原计划漂流，因为 `<已核验原因>`。**推荐改期到首个条件合适的日期**；也可以选择明天改为桐庐室内/低风险活动，或结束规划。你可以直接说“按推荐继续”。

### 可以继续

若有多个可行漂流点，先做候选 HITL：

> **推荐：`<漂流点 A>`**，因为 `<与同行者、天气、开放状态和交通相关的依据>`。你可以选：
> 1. 按推荐继续；
> 2. `<漂流点 B>`；
> 3. 调整刺激程度或同行者要求后再选。

用户确认后，后续所有查询都使用该明确入口。

## 3. 确认怎么去，再查路线

根据出发地、人数、当天往返或过夜安排给出交通 HITL：

> **推荐：`<交通方式>`**，因为 `<本次约束下的依据与取舍>`。你可以选：
> 1. 按推荐继续；
> 2. 自驾；
> 3. 公共交通，接受高铁/公交加打车的分段路线。

确认后才调用对应路线 Tool。公共交通按实际需要拆成“出发地到桐庐交通节点”“交通节点到景区入口”等路线段。每段原样保存 Tool 返回的高德 Markdown 导航链接；未返回时，该段写“暂无可用导航链接”。不得手工拼接或跨路线段复用链接。

若路线证据推翻了原推荐，说明新证据和取舍，再让用户确认是否切换。

## 4. 确认住宿要求，再查酒店

用户选择过夜时才进入住宿 HITL：

> **推荐：住一晚，优先选择 `<少绕路的住宿区域与暂定档位>`**，因为 `<活动结束时间、返程压力或次日安排依据>`。你可以选：
> 1. 按推荐继续；
> 2. 当天往返；
> 3. 住一晚，并告诉我预算、房间数/床型、想靠近漂流点还是交通/餐饮区，以及是否有偏好的酒店品牌。

房间数、床型、儿童入住和无障碍需求会影响库存，缺失时必须确认。软偏好缺失且用户授权“按推荐继续”时，才采用已展示的暂定档位和区域。

确认日期、入住配置和区域锚点后调用 `lodging_search`。最终只列本轮返回的候选和价格口径：

- `<酒店 A>`：`<每晚价/总价口径>`；查看/预订：`<该候选 booking_url>`
- `<酒店 B>`：`<每晚价/总价口径>`；查看/预订：暂无可用预订链接

不得用地图酒店 POI 或联网搜索补写候选、价格、库存和 OTA 链接。用户当天往返时跳过住宿查询。

## 5. 分别确认景点和餐饮

路线和住宿确定后，先只问景点：

> **推荐：增加 1 个顺路、低绕行的 `<景点类型>` 活动**，因为 `<剩余时间、地理位置和体力依据>`。你可以选：按推荐继续、改选自然山水/人文古村/亲子休闲，或只漂流和休息。

确认后只搜索少量顺路候选。运营事实查官方来源，攻略或 UGC 只用于体验与避坑建议。

景点确定后，再只问餐饮：

> **推荐：选择当前路线附近的本地特色餐饮**。请先说明是否有过敏或忌口；然后可以按推荐继续，或改选清淡家常、亲子友好及其他类型。

确认硬约束和类型后，再用周边搜索寻找餐饮 POI；位置关系来自地图，营业状态需用当前来源核验。

## 6. 最终答复骨架

### 方案摘要

- 明天是否可成行、首选漂流点和主要取舍。
- 当天往返或住一晚。
- 仍可能改变方案的最大不确定性。

### 天气与成行条件

- 覆盖目标日期的天气及来源状态。
- 开漂、预约、票务和同行者限制的核验结果。
- 装备建议和出发前复查节点。

### 怎么去

- 每个路线段的方式、参考耗时、换乘与缓冲。
- 紧邻各路线段原样展示其高德 Markdown 导航链接；没有时写“暂无可用导航链接”。

### 住宿

- 仅展示 `lodging_search` 本轮候选、价格口径和关键通勤。
- 每个候选紧邻展示自己的 `booking_url`；没有时写“暂无可用预订链接”。

### 景点与餐饮

- 少量顺路安排，区分已核验运营事实与攻略性建议。
- 标明餐饮营业状态以及过敏、忌口等硬约束。

### 待确认与下一步

- 用户需自行完成的景区预约、购票和 OTA 酒店预订。
- 出发前仍需复查的天气、开漂公告、交通或营业信息。

## 停止条件

- 用户只问天气、路线或酒店时，回到快速查询，不机械展开完整方案。
- 用户未回答当前 HITL 时，等待回复，不提前询问后续偏好或调用依赖查询。
- 可成行性门未通过时，不继续消耗路线、住宿、景点和餐饮查询。
- 工具失败或实时证据不足时，标为待确认，不用常识补造事实或链接。
