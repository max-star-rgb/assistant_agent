# 示例：用户说“我想明天去桐庐漂流”

本例只说明决策顺序，所有实时事实必须重新查询。

## 先查，不复述流程

把“明天”解析为用户时区下的绝对日期。先搜索实际漂流点，并查询目标日期天气、开漂公告、预约和同行限制。信息不足时，
执行 Agent 可先完成不依赖出发地的查询；不要先向用户解释内部步骤。

如果无法确定具体漂流点，只问当前选择：

> 桐庐有多个漂流点。推荐 `<候选 A>`，因为 `<已核验依据>`；也可以选 `<候选 B>`。你想按推荐继续吗？

如果天气或运营条件不允许：

> `<日期>` 暂不建议漂流：`<已核验原因>`。推荐改到 `<可行日期>`；也可以把当天改成 `<低风险替代活动>`。

到这里停止，不继续查酒店和详细路线。

## 可成行后逐项决定

漂流点确定后，交通查询缺少出发地时再问：

> 你从哪里出发？请给城市和大致区域即可。

查到交通事实后直接给推荐和备选；用户确认后再规划路线。每个路线段原样展示 Tool 返回的高德 Markdown 导航链接。

只有用户选择过夜时才确认入住人数、房间数、床型和必要限制，再调用 `lodging_search`。每家酒店只展示本轮结果中的价格
口径和自己的 `booking_url`。

路线与住宿确定后，分别询问景点、餐饮偏好；每轮只推进当前一项，并给默认推荐。选择餐厅前确认过敏和忌口。

## 最终交付

按“成行条件—往返路线—核心活动—住宿（如有）—顺路景点与餐饮—待复查事项”给出两日方案。区分实时核验事实和攻略
建议；缺少天气覆盖、运营公告、酒店链接或导航链接时明确标注，不自行补造。
