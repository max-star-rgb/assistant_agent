# 旅行决策与行程编排

把出行意图变成有实时依据、可执行的方案。Skill 只提供决策知识；需要酒店、地点或路线工具时，执行 Agent 独立激活
`travel` Tool Profile，天气工具保持独立可见。

## 决策顺序

1. **先用已有信息**：不要重复确认用户已明确的日期、出发地、天数或交通偏好。
2. **先查公共事实**：交通是否存在、天气、开放状态和运营限制应由工具核验，不要让用户回答。只有缺失信息会阻塞
   下一次查询时才提问；例如日期会影响班次和预报，人数通常不阻塞首次交通或天气查询。
3. **一次推进一个选择**：查询结果确实依赖用户偏好时，只问当前决策，给出一个默认推荐和少量备选。安全限制在选择
   活动前确认；人数、房间数和床型在查酒店前确认；过敏和忌口在查餐饮前确认。
4. **先排固定项**：先放置抵离时间和核心活动，再按邻近区域安排住宿、景点和餐饮，并保留换乘与休息缓冲。
5. **直接交付**：每次用户可见回复只有两种形状：`已核验事实 + 推荐 + 至多一个当前问题`，或在查询确实被缺失
   信息阻塞时只给`一个具体问题`。回复从事实或问题直接开始，不添加准备查询什么、为何遵循该流程或之后做什么的说明。

强天气或运营依赖活动不可行时，先给依据、改期或替代方案，不继续查询依赖该活动的酒店和详细路线。单点问题只回答
单点，不机械展开完整行程。

## 来源与链接

- 酒店候选、价格、库存和预订链接只使用本轮 `lodging_search` 结果；每家酒店紧邻展示自己的 `booking_url`，缺失时写
  “暂无可用预订链接”。
- 地点和路线使用地图工具核验；每个路线段原样保留路线 Tool 返回的高德 Markdown 导航链接，缺失时写“暂无可用导航链接”。
- 天气优先使用 `mcp_amap_maps_maps_weather`；预报未覆盖目标日期时标为待确认。
- 开放、票务、预约、临时公告和交通管制优先使用运营主体或官方来源；攻略和 UGC 只支持体验与避坑建议。

不得手工拼接链接，也不得用常识补造天气、价格、库存、营业状态、路线耗时或 URL。工具失败时明确缺失项，并继续完成
不依赖该结果的部分。
