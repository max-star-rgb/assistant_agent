# 旅行决策与行程编排

把用户偏好转成可执行的住宿、通勤或旅行方案。先锁定硬约束和固定时间，再对最终候选补充必要证据；输出必须区分已核验信息、攻略性建议和待确认事项。

## When to Use

- 查询或比较住宿、酒店价格、库存、房型、位置、通勤和 OTA 候选。
- 规划机场、车站、酒店、会议地、景点之间的步行、骑行、驾车或公共交通。
- 生成单日或多日、按上午/下午/晚上或具体时间段组织的完整旅行行程。
- 查询目的地、景点、周边、天气，以及需要当前开放、预约、门票、临时关闭或活动信息的旅行任务。

## When Not to Use

- 与旅行或出行无关的写作、翻译或闲聊。
- 只需回答用户已经提供的旅行文本，不需要查询、比较或规划。
- 不把 OTA 跳转解释为代订、锁价、付款或成交；当前能力只提供预订前决策支持。

## Task Modes

- **快速查询**：单个地点、天气或路线问题，只完成该目标，不扩展成完整攻略。
- **住宿决策**：按日期、入住人数、房间数、预算、房型、位置和通勤筛选并比较候选。
- **通勤比较**：围绕固定目的地比较候选住宿或交通方式，优先保护准时到达这一硬约束。
- **完整规划**：先安排抵离和预约等固定锚点，再按区域组织每天的时间块、交通、休息和备选方案。

## Quick Reference

| 需要回答的事实 | 首选来源 | 能支持的结论 |
| --- | --- | --- |
| 指定日期酒店价格、库存、OTA 链接 | `lodging_search` | 候选与工具实际返回的报价口径、跳转入口 |
| 地点名称、类型、地址、坐标、周边 | 地图地点或周边搜索 | POI 识别、区域和空间关系 |
| 步行、骑行、驾车、公共交通 | 对应路线工具 | 工具支持时间语义下的路线参考 |
| 旅行日短期天气 | 天气工具 | 返回项明确覆盖日期的预报 |
| 开放、预约、票务、临时公告 | Provider-native 搜索中的官方来源 | 与来源适用日期匹配的当前运营事实 |
| 游玩时长、体验、拥挤和避坑 | 攻略、OTA、UGC | 攻略性建议，不是官方承诺 |

## Decision Rules

- 把日期、抵离时间、固定活动、人数、房间数、预算上限、必须到访、无障碍和最晚到达视为硬约束；把风格、景观、热闹程度和一般偏好视为软约束。只在缺失信息会阻止查询或明显改变方案时澄清。
- 不自行把“每晚不超过 X”改写成含税价、最终成交价或总预算。保留 `nightly_price`、`total_price`、`price_basis` 和 Provider 提示的实际口径。
- 酒店价格、库存和 OTA 链接使用 `lodging_search`。`nearby_poi` 只是位置偏好；严格步行时间、通勤时间或半径必须对最终候选使用地图或路线结果核验。
- 地点发现和消歧使用文本或周边搜索；路线工具缺经纬度时才调用地理编码。区域名称不是唯一落点时，选用明确入口或交通节点并说明。
- 当前开放时间、预约、票务、临时关闭、节庆活动和交通管制需要当前信息。Provider-native 联网搜索可用时，优先查运营主体或官方来源；OTA、攻略和 UGC 用于发现玩法、体验和常见问题，不替代官方运营事实。
- Provider-native 联网搜索不是本地 Tool，不进入 Governed Tools。搜索回复没有可识别来源或适用日期时，只能作为攻略性建议或待确认事项，不能标为已核验。
- 多日行程先放置航班、火车、会议、演出和预约等不可移动锚点，再按相邻区域聚类景点；只对准备纳入最终方案的候选核验开放和路线，避免为全部候选重复搜索。
- 路线结果没有未来出发时间语义时，只表述为当前规划参考。为进出站、安检、排队、找路、换乘、用餐和同行者体力预留可见缓冲，不用压缩缓冲伪造可行性。
- 天气工具未覆盖旅行日期时，不用相邻日期或气候均值冒充预报；把天气安排标记为待出发前复查。

## Procedure

1. 判断任务模式，整理一份内部约束表：目的地、日期、抵离时间、人数与房间、预算口径、固定活动、交通偏好、节奏、兴趣和特殊需求。
2. 对住宿决策先调用 `lodging_search` 获得真实日期候选；需要比较通勤时，先按住宿硬约束缩小候选，再核验最终候选到固定目的地的路线。
3. 对完整规划先放置固定时间锚点和入住、退房、寄存、返程边界，再发现景点、餐饮区域或活动候选。
4. 需要当前运营信息时使用 Provider-native 联网搜索；把官方运营事实、地图路线事实、OTA 报价和 UGC 体验分别记录，不混成同一种证据。
5. 按区域和相邻关系给每天分组，再为每个时间块安排活动、移动、用餐、休息和必要缓冲。慢节奏、老人、儿童或无障碍需求应降低每日密度。
6. 用路线工具检查相邻时间块和关键通勤是否可达；如果全部要求排不下，指出冲突并给出删减或替代方案。
7. 查询旅行日天气；预报不可用或日期过远时，提供室内备选并标记复查时间，不生成具体天气事实。
8. 做一次完整性检查后回答：硬约束是否满足、固定时间是否冲突、酒店和路线是否对应同一候选、当前事实是否有来源、链接是否真实来自本轮结果。

## Output Contract

- 快速查询只回答相关目标；住宿比较或完整规划才使用下面的对应结构。
- **方案摘要**：首选方案、主要取舍和没有满足的约束。
- **关键假设**：只列会影响价格、时间或可行性的假设。
- **住宿比较**：候选、每晚价、总价口径、位置与关键通勤、优缺点、对应 OTA 链接。没有 `booking_url` 时明确无可用跳转，不创建搜索链接或酒店详情 URL。
- **每日行程**：按日期和时间段列活动、地点、交通方式、预计移动时间、缓冲及核验状态；抵达日和返程日不得按完整游玩日塞满。
- **信息状态**：将内容标为“已核验信息”“攻略性建议”或“待确认事项”。时间敏感事实在来源可用时附官方或原生搜索返回的链接。
- **下一步**：列出需要用户在 OTA 或官方渠道自行完成的查看、预约或购买操作，不声称已经代为完成。

## Pitfalls

- 不在工具或搜索尚未返回时预写具体酒店、价格、开放时间、路线耗时、天气或 URL。
- 不把地图酒店 POI 当成指定日期的房价和库存，也不把酒店描述中的“附近”当成严格通勤证据。
- 不从常识拼出 OTA 链接；只交付 `lodging_search` 本轮返回的 `booking_url`。
- 不照搬单篇攻略的现成行程；先应用用户硬约束、地理聚类、路线时间和体力节奏。
- 不把 UGC 的排队、好玩或推荐时长写成官方承诺，也不把缺少来源的搜索摘要写成当前规则。
- 不为了覆盖更多景点牺牲固定时间、交通缓冲、用餐和休息。不能全部容纳时明确建议删减。
- 不因一个查询失败放弃整个任务；继续完成不依赖它的部分，并把失败项放入待确认事项。

## Verification

- 任务模式正确：单点问题没有过度规划，完整旅行请求包含按天、按时间段的安排。
- 所有硬约束都已满足，或逐项说明冲突和最接近的替代方案；软偏好的取舍理由清楚。
- 酒店候选来自日期搜索，价格口径未被改写，严格位置或通勤要求已对实际候选核验。
- 每个相邻时间块在地理和时间上可行，抵离、入住退房、固定活动、用餐、休息和缓冲没有互相冲突。
- 当前开放、预约、票务和临时变更有适用日期与可识别来源；否则明确属于攻略性建议或待确认事项。
- 天气只使用覆盖旅行日期的预报；路线只按工具实际支持的时间语义描述。
- OTA 链接与候选一一对应；链接不代表锁价、库存保证、预订成功或最终成交。

## Example

用户要求“国庆带父母去杭州四天，选每晚 900 元以内的酒店，安排西湖、灵隐寺和博物馆，并给 OTA 链接”时：

1. 将抵离时间、三人入住、预算、父母慢节奏和必去地点写入约束表；房间数或床型会改变报价时先澄清。
2. 搜索真实日期酒店并缩小候选，只对最终候选核验车站、灵隐寺和博物馆通勤。
3. 使用原生联网搜索核验准备采用的景点开放、预约和节假日安排；无可靠来源的攻略时长只作为建议。
4. 先固定抵离和预约时间，把相邻景点按天聚类，加入午休、用餐和国庆交通缓冲，再准备雨天替代。
5. 输出酒店对比、按天时间表、已核验信息、攻略性建议、待确认事项及工具真实返回的 OTA 链接。
