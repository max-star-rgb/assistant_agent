# 旅行决策与行程编排

把宽泛的出行意图逐步变成可执行方案。先判断能否成行，再确认会改变查询结果的偏好；只交付有来源的事实和链接。

## 何时使用

- 酒店搜索、住宿比较、目的地通勤、路线导航、天气、景点或餐饮安排。
- 单点问题只做对应查询；多个活动或日期才展开完整行程。
- 只提供预订前决策支持，不声称已订房、购票、锁价或付款。

## 最短执行流程

1. **补最小硬约束**：提取已知的日期、出发地、天数、人数和固定安排；只追问会阻塞下一步的信息，不重复询问用户已经给出的内容。
2. **先过可成行性门**：对漂流、滑雪、登山等受天气或运营状态强影响的活动，先消歧具体地点，并核验目标日期的天气、开放、预约、临时关闭及同行者限制。若关键条件不成立，停止展开酒店、路线、景点和餐饮，先给改期或替代方案。
3. **渐进式 HITL**：可成行后，一次只确认当前决策。通常依次为活动候选、交通方式、住宿要求、景点类型、餐饮类型。每轮给出一个有依据的默认推荐、简短理由、少量选项和“按推荐继续”；用户已明确偏好时跳过该轮。
4. **查询并组装**：用户确认后才执行依赖该选择的查询。先放置固定活动和抵离时间，再按相邻区域安排活动，并为换乘、排队、用餐和休息留出缓冲。
5. **交付并标注状态**：区分“已核验信息”“攻略性建议”“待确认事项”，只回答当前任务所需范围。

这里的 HITL 是对话式偏好确认，不是非 read Tool 的审批 interrupt。过敏、忌口、无障碍、儿童限制，以及会影响库存的房间数、床型和入住配置属于硬约束，不能用默认推荐代替确认。

## 来源与链接规则

- **酒店**：价格、库存、候选和 OTA 链接只使用本轮 `lodging_search` 结果，并保留其价格口径。每个候选展示自己的 `booking_url`；没有时写“暂无可用预订链接”。
- **地点与路线**：地点发现和消歧使用地图搜索，严格通勤要求需对最终候选核验。每个路线段原样保留路线 Tool 返回的高德 Markdown 导航链接；没有时写“暂无可用导航链接”。
- **天气**：优先使用 `mcp_amap_maps_maps_weather`；结果不足时再用 Provider-native 联网搜索核验权威气象来源。预报未覆盖目标日期时必须标为待确认。
- **运营事实**：开放、票务、预约、临时公告和交通管制优先使用运营主体或官方来源。
- **攻略建议**：攻略、OTA 或 UGC 只能支持体验、拥挤和避坑建议，不能替代实时运营事实。

不得手工拼接、改写或复用酒店和导航链接，也不得用常识补造天气、房价、库存、营业状态、路线耗时或 URL。查询失败时继续完成不依赖该结果的部分，并明确缺失项。

## 输出要求

- 快速查询：直接回答目标问题，并给必要的来源状态或链接。
- 完整规划：依次给方案摘要、天气与成行条件、路线、住宿、景点与餐饮、待确认事项和下一步。
- 酒店链接紧邻对应酒店；高德导航链接紧邻对应路线段。
- 若硬约束冲突或时间排不下，明确冲突并建议删减，不压缩必要缓冲来伪造可行性。

## 完成检查

- 是否先核验了强天气或运营依赖活动的可成行性？
- 是否只询问当前必要决策，并保护了安全、库存和无障碍等硬约束？
- 酒店、路线、天气和运营事实是否来自正确来源并正确标注状态？
- 每个酒店和路线段是否展示自身链接或明确说明无可用链接？
