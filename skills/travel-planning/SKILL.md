# 旅行规划

目标是先把宽泛的出行想法逐步规划清楚，再根据用户确认的计划查询实时事实并形成可执行方案。需要搜索酒店、地点或路线时
激活 `travel` Tool Profile；天气查询可直接使用独立暴露的天气工具。

## 先确认需求

- 复用用户已经给出的日期、出发地、人数、天数和交通偏好，不重复确认。
- 用户要求完整旅行规划但关键信息不足时，先通过自然对话明确需求，不调用天气、地图、酒店等业务工具或发布执行任务。
- 通常依次确定出发地与交通方式、同行人数与活动安全条件、是否住宿及住宿偏好、餐饮忌口与口味。同一方面紧密相关的
  缺口可以合并成一个自然问题。
- 只输出当前需要确认的问题本身，不解释提问原因，不复述记忆、Skill 规则、已知或未知字段、内部判断及后续步骤。
  长期记忆只用于避免无意义的重复询问，不能代替用户在当前对话中确认人数、交通、住宿等关键计划参数。
- 全部关键选择确定后，给出包含明确日期、人员、交通、住宿和餐饮偏好的简短计划摘要，并询问是否开始执行；确认计划的
  回复中不得同时查询或执行。
- 用户只问一个单点问题时只解决该问题，不机械展开其他旅行事项。

## 确认后查询

- 只有用户明确确认计划或要求开始执行后，才查询实时事实、激活 Tool Profile 或发布执行任务。委派说明必须包含已经确认的
  完整计划和本次执行目标，不让子 Agent 猜测人数、交通、住宿或餐饮偏好。
- 先核验天气、交通可达性、开放状态、运营限制和核心活动，再安排邻近的住宿、景点和餐饮，并为换乘、用餐和休息留出余量。
- 回复从已核验事实或明确建议开始，不向用户复述内部分析、工具计划或工作流程。

如果天气、运营或安全条件使核心活动不可行，给出依据和改期或替代建议，暂不继续查询依赖该活动的酒店与详细路线。

## 事实与链接

- 酒店名称、价格、库存和预订链接只使用本轮 `lodging_search` 结果。每家酒店旁边展示自己的 `booking_url`；没有链接时
  明确写“暂无可用预订链接”。
- 地点和路线使用地图工具核验。每个路线段原样保留工具返回的高德 Markdown 导航链接；没有链接时明确写“暂无可用导航链接”。
- 天气优先使用 `mcp_amap_maps_maps_weather`；预报未覆盖目标日期时标为待确认。
- 开放、票务、预约、临时公告和交通管制优先使用运营主体或官方来源；攻略和 UGC 只支持体验与避坑建议。

不要手工拼接链接，也不要用常识补造天气、价格、库存、营业状态、路线耗时或 URL。查询失败时说明缺失了什么，并继续
完成不依赖该结果的部分。

## 示例

遇到“明天我想去安吉漂流”这类只有日期、目的地和活动的请求时，读取
`/travel-planning/references/anji-rafting-example.md`。其中的具体名称、时间、价格和查询结果只用于演示交互，不代表实时
事实，实际执行时必须重新查询。
禁止向用户透露你参考了示例。
