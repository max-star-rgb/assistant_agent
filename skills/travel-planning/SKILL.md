# 旅行规划

目标是把宽泛的出行想法逐步变成有实时依据、能直接执行的方案。需要搜索酒店、地点或路线时激活 `travel` Tool
Profile；天气查询可直接使用独立暴露的天气工具。

## 推进原则

- 复用用户已经给出的日期、出发地、人数、天数和交通偏好，不重复确认。
- 天气、交通可达性、开放状态和运营限制属于公共事实，应先查询。只有缺失信息会阻塞下一项查询时才问用户。
- 需要用户选择时，只推进当前最重要的决定，给出一个有依据的默认推荐和少量备选。同一决定中紧密相关的缺口可以合并成
  一个自然问题，但不要同时开启住宿、景点、餐饮等后续主题。活动安全条件优先于体验偏好；住宿前再确认人数、房间和
  床型，餐饮前再确认过敏、忌口和口味。
- 先确定往返时间与核心活动，再安排邻近的住宿、景点和餐饮，并为换乘、用餐和休息留出余量。
- 回复从已核验事实、明确建议或一个具体问题开始，不向用户复述内部分析、工具计划或工作流程。

如果天气、运营或安全条件使核心活动不可行，给出依据和改期或替代建议，暂不继续查询依赖该活动的酒店与详细路线。
用户只问一个单点问题时，只解决该问题。

## 事实与链接

- 酒店名称、价格、库存和预订链接只使用本轮 `lodging_search` 结果。每家酒店旁边展示自己的 `booking_url`；没有链接时
  明确写“暂无可用预订链接”。
- 地点和路线使用地图工具核验。每个路线段原样保留工具返回的高德 Markdown 导航链接；没有链接时明确写“暂无可用导航链接”。
- 天气优先使用 `mcp_amap_maps_maps_weather`；预报未覆盖目标日期时标为待确认。
- 开放、票务、预约、临时公告和交通管制优先使用运营主体或官方来源；攻略和 UGC 只支持体验与避坑建议。

不要手工拼接链接，也不要用常识补造天气、价格、库存、营业状态、路线耗时或 URL。查询失败时说明缺失了什么，并继续
完成不依赖该结果的部分。
