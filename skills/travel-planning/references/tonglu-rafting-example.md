# 示例：用户说“我想明天去桐庐漂流”

所有天气、运营、交通、酒店和营业信息都必须按用户的实际日期重新查询。

## 先判断能否漂流

把“明天”换算成用户时区下的具体日期，搜索桐庐实际可选的漂流点，并核验天气、开漂公告、预约要求和年龄等限制。
这些查询不依赖出发地，不必先向用户提问。

多个漂流点都可行时，先给出推荐依据，再确认当前选择：

> 桐庐有多个漂流点。推荐 `<候选 A>`，因为 `<已核验依据>`；也可以选 `<候选 B>`。你想按推荐继续吗？

天气或运营条件不允许时，直接给替代方案：

> `<日期>` 暂不建议漂流：`<已核验原因>`。推荐改到 `<可行日期>`；也可以把当天改成 `<低风险替代活动>`。

此时停止，不查询依赖漂流活动的酒店和详细路线。

## 可成行后按需求继续

确定漂流点后，如果不知道出发地，只问：

> 你从哪里出发？给我城市和大致区域即可。

查到交通事实后给出推荐方式和一个备选，用户确认后再展开分段路线；每段原样展示工具返回的高德 Markdown 导航链接。

先回答用户当前关心的可成行性或交通问题。只有用户要求完整规划，或往返时间客观上可能需要过夜时，才继续安排住宿、
景点和餐饮。

需要决定是否过夜时，推荐一个更符合时间安排的方案，并确认当天往返还是住一晚。选择过夜后，再确认入住人数、房间数、
床型和必要限制，然后调用 `lodging_search`；每家酒店只展示本轮结果中的价格口径和自己的 `booking_url`。

用户还需要景点和餐饮建议时，优先安排顺路选项。偏好会显著改变结果时才问，每次聚焦当前决定并给默认推荐；选餐厅前
确认过敏和忌口。

## 最终交付

用户要求完整方案时，交付成行条件、往返路线、核心活动、住宿（如有）、顺路景点与餐饮以及出发前待复查事项。区分实时
核验事实和体验建议；缺少天气覆盖、运营公告、酒店链接或导航链接时明确标注。
