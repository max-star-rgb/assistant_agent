## 🔴 必考题（必须背下来）

### 1. context_summary vs 长期记忆

| 维度 | context_summary | 长期记忆 |
|-----|----------------|---------|
| 所属模块 | 上下文工程 | 记忆服务 |
| 生命周期 | 会话级 | 持久化 |
| 写入控制 | 自动生成，不写长期记忆 | 必须策略校验 |
| 中间状态 | 无 | MemoryPromotionCandidate |

**口诀**：会话内用 summary，跨会话用记忆，候选先审计。

---

### 2. 裁剪优先级顺序

```
记忆 → 对话 → 工具观察
```

**三个设计维度**：
1. 证据时效性（工具 = 刚发生的事实）
2. 可恢复性（记忆/对话可恢复，工具不可恢复）
3. 错误成本（工具裁掉 = 任务直接失败）

---

### 3. 6 类绝对不能进 prompt 的内容

| 类型 | 一句话 |
|-----|-------|
| 敏感凭证 | API key、token、密码、cookie |
| 原始 provider payload | OpenAI 完整响应，别把服务商的东西喂回去 |
| base64 / data URI | 一张图顶几千 token，疯了才往里塞 |
| raw HTML | 几十 KB 标签，纯噪音 |
| raw media / file | 二进制 LLM 根本读不懂 |
| 本地敏感路径 | .ssh、C:\Users 别漏出去 |

---

### 4. 记忆幻觉排查流程

```
查 prompt → 查 retrieval trace → 查 context_summary → 查 memory store → 查 write policy
```

**5 种根因**（概率从高到低）：
1. embedding 检索误召 ⭐⭐⭐⭐⭐
2. context_summary 压缩失真 ⭐⭐⭐⭐
3. 记忆提升策略太松 ⭐⭐⭐
4. ToolObservation 被误判 ⭐⭐
5. 跨会话串扰 ⭐

## 🟡 高频题（记核心点）

### 优化优先级（ROI 从高到低）

1. **修复 token 计数逻辑**（改一行，省 30%）
2. 工具观察分级裁剪（90% 膨胀来自这里）
3. 对话历史分层保留（最近 2 轮原文，中间摘要，最早丢弃）
4. 自适应压缩触发（梯度压缩，不是到点突然砍）
5. 记忆分池 + 阈值过滤
6. LLM 增量摘要（最后才用，因为贵）

---

### 4 种压缩方式对比

| 方式 | 速度 | 成本 | 质量 | 适用 |
|-----|------|------|------|------|
| 确定性截断 | 超快 | 0 | 最差 | 工具输出、长列表 |
| 提取式摘要 | 快 | 低 | 一般 | 中等对话 |
| LLM 抽象摘要 | 慢 | 高 | 最好 | 长对话压缩 |
| 滑动窗口滚动摘要 | 中 | 中 | 好 | 超长 20+ 轮 |

### 工具调用 4 层抽象

```
ToolSpec（是什么）→ ToolSelection（选了啥）→ ToolResult（原始输出）→ ToolObservation（给 LLM 看的）
```

**本项目特有设计**：
- `when_to_use` / `when_not_to_use` - 把最佳实践写死
- `next_step_hint` - 直接告诉 LLM 下一步干啥
- `output_ref` 引用机制 - 大输出不进 prompt，用 artifact 存

## 🟢 加分题（答出来直接拉开差距）

### 防幻觉 3 层防御

1. **检索层**：双阈值 + 来源标记（`[用户说过]` / `[工具返回]` / `[Agent 思考]`）
2. **注入层**：边界 fence + 指令强化（明确告诉 LLM 这是历史记忆，不是当前对话）
3. **生成层**：引用 ID + 可溯源（每条记忆带 ID，LLM 必须标注引用）

**面试金句**：
> 记忆幻觉本质是边界问题，不是 LLM 傻，是系统没告诉它信息来自哪里。

### 自适应上下文管理 6 组件

1. 预算监控器（梯度触发，不是一刀切）
2. 场景分类器（纯聊天 / 工具调用 / 记忆密集，策略不同）
3. 压缩策略器（工厂模式选算法）
4. 裁剪执行器（带 undo 日志）
5. 组件注册器（优先级可配置，不硬编码）
6. 质量回标器（闭环反馈，自动调参）

## 🕳️ 生产环境踩坑篇

### 上下文裁剪后失忆问题

**根因**：裁剪是暗箱操作，LLM 既不知道被裁了，也不知道怎么处理信息缺失

**5 种缓解手段**：
1. 裁剪标记法 - 不是删掉，而是换成 `[上下文裁剪：省略了较早对话]`
2. 不可裁剪区 - 用户输入标记 `[DO_NOT_TRIM]`
3. 滚动摘要保留 - 裁掉的内容压缩成 1 句话摘要
4. 分栏上下文注入 - 明确标注哪部分是完整的，哪部分是摘要
5. 预算水位线标记 - `[当前上下文使用率 82%]`

**主动追问机制 3 步（修正版）**：
1. System Prompt 行为约束 - 明确禁止说"我记得你说过"，没看到就直接问
2. 裁剪关键词指纹 - 记录被裁内容的 3 个关键词，不丢太多信息也不占空间
3. Prompt 末尾加小提示 - 告诉 LLM 哪类话题可能被裁了，让它自己判断要不要追问

**关键认知**：不要事后拦截输出，要事前告诉 LLM 游戏规则

**面试金句**：
> 裁剪的本质不是"删"，而是"降级"。好的裁剪系统让用户在信息缺失时能被温柔提醒，而不是看 AI 突然失忆。

## ⚙️ Agent Runtime 核心流程篇

### "内存里有，prompt 里没有"问题

**5 种根因（按排查顺序）**：
1. ConversationStore 注入时只取最近 N 轮（默认最近 2 轮原文 + 较早摘要）
2. 上下文摘要压缩把关键信息弄丢了
3. 分栏渲染时被放到了"记忆块"里，LLM 注意力没覆盖到
4. AgentState 状态不一致 / 多线程污染
5. 上游 API / websocket 丢包

**上下文完整生命周期 7 层**：
```
ConversationStore → 会话注入 → MemoryManager注入 → 上下文组装 → 预算计算 → 裁剪执行 → Prompt渲染
```

**Debug 工具设计思想**：每一层拍一张快照，最后 diff，让问题主动跳出来，不要让开发瞎找。

## 🏗️ 边界设计篇

### 上下文工程 vs 记忆模块边界划分

**4 个拆开来的好处（架构师视角）**：
1. 团队边界解耦 - prompt 优化团队 vs 数据平台团队，迭代节奏不同
2. 测试边界解耦 - 上下文用 mock 记忆测，记忆单独测准确率，互不依赖
3. 供应商切换成本低 - 换 LLM 只改渲染层，换向量库只改记忆层
4. 故障隔离 - 记忆服务挂了，上下文可以降级成空记忆运行，整个系统不崩

**3 个拆开后的缺点（真实坑）**：
1. 双重写入策略冲突 - 上下文和记忆都有自己的保留策略，可能两边都丢
2. 数据一致性难题 - 同一份对话在 3 个地方存了 3 份，可能不一致
3. 重复计算浪费 - token 计数算一遍，embedding 再算一遍，两遍都花钱

**边界划分 3 条军规**：
1. 数据所有权清晰 - ConversationStore 是唯一真相来源，其他都是缓存
2. 策略不重叠 - 最近 N 轮上下文管，N 轮以前记忆管，中间无重叠区
3. 交互只有一次 - 上下文组装时调用一次记忆接口，后续不再回调

**架构师金句**：
> 好的边界划分不是看"代码放哪个目录"，而是看"出了 bug 谁背锅"。

## 💡 万能套话（实在不会就说这个）

- **上下文工程的本质**：信息经纪人，在正确的时间、给正确的角色、提供正确粒度的信息
- **工程取舍原则**：宁少勿错，但求必应。宁可少塞一点，也别塞错东西导致任务失败
- **优化指导思想**：按 ROI 排序，先做改一行代码省 30% 的，最后做改一万行省 5% 的
