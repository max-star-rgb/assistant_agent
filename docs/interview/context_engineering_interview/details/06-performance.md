# 五、性能优化篇 - 详情

---

## 🟡 原题

你负责的 Agent 系统上线后发现：95% 的用户对话都在 3 轮以内，但有 5% 的长对话会跑 10+ 轮，导致这部分请求上下文越来越大，LLM 调用延迟从 2s 升到了 8s，成本也翻了 3 倍。

请回答：
1. 你会从哪几个维度切入优化？请按优先级排序
2. 上下文压缩有哪几种实现方式？各有什么 trade-off？
3. 如果让你设计一个"自适应上下文管理系统"，它应该有哪些核心组件？

---

## Q1. 长对话上下文膨胀的优化策略 🟡

### 【我的回答】
1.在上下文达到一定阈值后，删除记忆;删除较早轮次的对话;轻量压缩;更严格的压缩。2.基于代码规则的压缩，对结构化字段采取白名单式的保留;或者基于LLM对上下文进行压缩。前者确定但死板，后者灵活能保留关键信息，但耗时耗token。3.无法回答。

### 【面试官点评】

✅ **答对的部分**：

❌ **不足的地方**：

2. 第1题漏掉了"优化 token 计数"这个性价比最高的手段
3. 第3题没答出来，这是区分"高级工程师"和"架构师"的核心题

### 【标准答案】

#### 1. 优化优先级排序（按 ROI 从高到低）

记住：95% 的请求是短对话，优化不能影响它们！

| 优先级 | 优化手段 | 为什么排在这里 | 投入产出比 |
|-------|---------|--------------|-----------|
| **P0** | **修复 token 计数逻辑** | 很多项目用字符数估算 token，误差高达 30%！往往是"以为超了"其实没超。这是改一行代码就能见效的事，最划算 | ⭐⭐⭐⭐⭐ |
| **P1** | **工具观察结果分级裁剪** | 90% 的上下文膨胀来自工具输出（商品列表、长文本），而且裁剪对效果影响最小 | ⭐⭐⭐⭐⭐ |
| **P2** | **对话历史分层保留** | 最近 2 轮保留原文，中间的保留摘要，最早的直接丢弃。用户对早期对话的遗忘速度比 LLM 还快 | ⭐⭐⭐⭐ |
| **P3** | **自适应压缩触发** | 不是到了阈值才压缩，而是超过阈值比例后每轮都增量压缩。比如超过 80% 后每轮压缩一轮对话，而不是等到 100% 突然压掉一半 | ⭐⭐⭐ |
| **P4** | **记忆分池 + 阈值过滤** | 不是删记忆，而是把记忆分成"用户画像池"和"任务上下文池"，当前任务只召回相关池的记忆。相似度低于阈值的记忆根本不注入 | ⭐⭐⭐ |
| **P5** | **LLM 增量摘要** | 最后才用 LLM 压缩，因为这本身就多花一次 LLM 调用 | ⭐⭐ |

**面试金句**：
> "优化上下文不是'谁不重要就删谁'，而是**在用户感知不到质量下降的前提下，用最小的工程代价换最大的 token 节省**。"

#### 2. 上下文压缩的 4 种实现方式与 trade-off

不止 2 种，工业界实际有 4 种：

| 方式 | 实现原理 | 优点 | 缺点 | 适用场景 |
|-----|---------|------|------|---------|
| **1. 确定性截断** | 按优先级裁剪，工具观察留重点，旧对话直接删 | 0 延迟，0 成本，完全可复现 | 容易丢失关键细节，体验不稳定 | 工具输出、长列表、90% 的普通场景 |
| **2. 提取式摘要** | 用 TF-IDF / TextRank 算法从原文中提取关键句子 | 比截断聪明，不会"断章取义"，速度快 | 还是不如 LLM 懂语义，可能漏掉"看起来不重要但实际很关键"的信息 | 中等长度对话，追求速度 |
| **3. LLM 抽象式摘要** | 让 LLM 重新写一遍摘要，不限制原文句子 | 语义理解最好，能跨句子归纳 | 贵、慢、本身就占 token，而且引入了新的幻觉来源 | 长对话压缩，质量优先 |
| **4. 滑动窗口 + 滚动摘要** | 每轮只压缩最早的一轮对话，摘要和新的摘要合并，而不是全量重新压缩 | 增量压缩，延迟稳定，上下文不会"跳崖式"突然变短 | 实现复杂，累计误差可能导致信息丢失 | 超长对话（20+ 轮） |

#### 3. 自适应上下文管理系统的核心组件

这是一个完整的设计，面试时能说出 4 个以上就算优秀：

```
┌─────────────────────────────────────────────────────────┐
│              自适应上下文管理器                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────────┐    ┌──────────────┐    ┌────────────┐
│  │  预算监控器  │ →  │  压缩策略器  │ →  │  裁剪执行器│
│  └──────────────┘    └──────────────┘    └────────────┘
│         ↑                   ↑                   ↑
│  ┌──────────────┐    ┌──────────────┐    ┌────────────┐
│  │  质量回标器  │    │  场景分类器  │    │  组件注册器│
│  └──────────────┘    └──────────────┘    └────────────┘
│                                                         │
└─────────────────────────────────────────────────────────┘
```

| 组件 | 职责 |
|-----|------|
| **预算监控器** | 实时计算当前 token / 字符使用率，不是到了阈值才触发，而是按梯度：<br>- 50%：什么都不做<br>- 70%：开始裁剪工具观察<br>- 85%：开始压缩旧对话<br>- 95%：开始过滤低相似度记忆 |
| **场景分类器** | 识别当前对话类型，不同场景用不同策略：<br>- 纯聊天：对话优先，记忆可以多删<br>- 工具调用任务：工具观察优先，宁可删对话<br>- 记忆密集型任务：记忆优先，宁可多花 token |
| **压缩策略器** | 抽象工厂模式，根据场景和预算自动选择：截断 / 提取式 / LLM 摘要 |
| **裁剪执行器** | 实际执行裁剪，带 undo 日志——如果裁剪后 LLM 说"我需要之前的信息"，可以恢复 |
| **组件注册器** | 各组件声明"我的裁剪优先级是多少"，不是硬编码在代码里 |
| **质量回标器** | 离线 A/B 测试：如果某轮压缩后用户纠错了，说明压缩过度，自动调整阈值 |

**核心设计思想**：
> "上下文管理不是一次性的静态裁剪，而是**每轮动态调整的闭环系统**——压缩多少，怎么压缩，压缩后效果好不好，系统自己会学习和调整。"
