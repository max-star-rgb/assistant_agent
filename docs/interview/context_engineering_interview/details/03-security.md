### 【标准答案】

#### 1. 绝对不能进入 prompt 的 6 类内容

| 类型 | 具体例子 | 为什么不能进 |
|-----|---------|------------|
| **敏感凭证** | API key、token、Authorization header、password、cookie | 直接泄漏给 LLM 服务商，也可能被模型输出给用户 |
| **原始 provider payload** | OpenAI/Gemini 等的完整响应体 | 包含大量冗余字段和 token 计数，还可能泄漏服务商内部错误信息 |
| **base64 / data URI** | `data:image/png;base64,iVBORw...` | 超级长（一张图 = 几十万个字符），直接撑爆上下文 |
| **raw HTML** | 完整的网页源码 | 几十 KB 的标签、CSS、JS，完全是噪音 |
| **raw media / file** | 原始图片、视频、音频二进制 | 非文本，LLM 根本读不懂 |
| **本地敏感路径** | `/home/user/.ssh/id_rsa`、`C:\Users\...` | 泄漏本地文件系统信息 |

#### 2. 为什么要裁剪？直接用原始数据不行吗？

3 个核心理由（按优先级排序）：

| 优先级 | 理由 | 后果 |
|-------|------|------|
| 1 | **安全隔离** | 把"Agent Runtime 可见的数据"和"LLM 可见的数据"做边界切割。Runtime 需要原始 payload 做错误处理，但 LLM 不需要。不隔离就是典型的"过度授权" |
| 2 | **预算控制** | 原始工具输出经常是几万字符级别，不裁剪的话一轮对话就打满上下文窗口 |
| 3 | **信噪比优化** | LLM 注意力有限，原始数据中的噪音（HTML 标签、base64、冗余字段）会严重干扰模型判断 |

**面试金句**：
> "上下文工程不是把所有东西都塞给 LLM，而是做**信息经纪人**——在正确的时间、给正确的角色、提供正确粒度的信息。"

#### 3. 裁剪过度 vs 信息完整的平衡机制（5 个经典机制）

| 机制 | 具体做法 |
|-----|---------|
| **白名单字段保留** | 不是"删什么"，而是"留什么"。例如商品搜索只保留：`title, price, url, platform, availability`，其他全删 |
| **分级裁剪** | `status`、`error`、`output_refs` 永远保留；`raw` 字段永远删除；中间字段按长度裁剪（字符串最多 1200 字符，列表最多 3 项） |
| **引用保留** | 不存完整内容，但存 `output_ref: artifact://xxx`，LLM 需要时可以用 `get_artifact` 工具重新获取完整内容 |
| **审计标记** | 裁剪后记录 `pruned_keys: ["raw_image", "base64", ...]`，如果 LLM 问"刚才的图片呢？"，系统知道是裁剪掉了，可以提示用户 |
| **策略可配置** | 不同工具用不同裁剪策略：搜索工具裁得狠，代码执行工具保留更多 stdout |

**一句话平衡原则**：
> "保留**决策必需的摘要**，删除**执行必需的细节**；如果细节不够，让 LLM 用工具主动取，而不是提前全塞进去。"
