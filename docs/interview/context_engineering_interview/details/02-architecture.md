# 二、架构设计篇 - 详情

---

## 🔴 原题

当上下文总字符超出预算时，系统会按优先级裁剪。请回答：

1. 裁剪的优先级顺序是什么？
2. **为什么**是这个顺序？背后的设计权衡是什么？
3. 如果让你重新设计这个优先级，你会调整吗？为什么？

---

## Q1. 上下文预算裁剪的优先级与设计权衡 🔴

### 【我的回答】
优先级顺序为：记忆、之前的对话文本、工具观察结果。因为agent最依赖工具结果来执行下一步，记忆和对话是为了更好的调用工具，记忆更多作为参考，对话文本反映了用户的意图。我不会调整，这样是较优的。

### 【面试官点评】

✅ **答对的部分**：
- 裁剪顺序完全正确：记忆 → 对话 → 工具观察
- 核心理由正确：工具观察是执行下一步的直接证据

❌ **不足的地方**：
1. **缺少具体的设计权衡维度**：没有从"证据时效性"、"可恢复性"、"错误成本"等维度展开
2. **缺少反例论证**：没有说明"如果先裁剪工具观察会发生什么"
3. **缺少场景化思考**：没有考虑特殊场景下是否需要调整（例如纯对话场景、纯记忆检索场景）

---

### 【标准答案】

#### 1. 裁剪优先级顺序（标准答案）

```
1. 记忆文本（memory_text）→ 最先裁剪
2. 对话文本（conversation_text）→ 其次裁剪
3. 工具观察结果（observations）→ 最后裁剪
```

#### 2. 背后的设计权衡（3 个核心维度）

| 维度 | 解释 |
|-----|------|
| **证据时效性** | 工具观察是"刚发生的事实"，记忆和对话是"历史信息"。LLM 决策严重依赖最近的工具输出，如果裁剪掉，Agent 可能重复调用工具或做出错误判断 |
| **可恢复性** | 记忆和对话丢了，还可以通过重新检索/用户追问恢复；但工具观察如果裁剪了，当前轮次无法恢复，必须重新执行工具 |
| **错误成本** | 裁剪记忆 → 回答不那么"个性化"；裁剪对话 → 可能漏掉用户意图；裁剪工具 → **直接导致任务失败** |

**一句话总结**：工具观察是**当前决策环的"栈帧"**，裁了就"栈溢出"了；记忆和对话是"堆内存"，丢了还能 GC 后重建。

#### 3. 是否需要调整？（辩证思考）

- 对 **90% 的 Agent 场景**（工具调用型任务）这是最优的，不需要调整
- 但有例外场景：
  - **纯对话场景**（没有工具调用）：可以调整为「记忆 → 工具观察 → 对话」
  - **纯知识问答场景**（强依赖历史记忆）：可以调整为「对话 → 工具观察 → 记忆」
