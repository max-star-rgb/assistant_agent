# HTTP Agent Run Gateway Migration Design

Date: 2026-07-08

## Goal

Move HTTP `/agent/run` behind Gateway while preserving the existing
`AgentRunResponse` contract.

The target path for this phase is:

```text
HTTP /agent/run
    -> identity and trial access checks
    -> GatewayTurnFacade
    -> GatewaySessionManager / GatewaySessionService
    -> GatewayAgentAdapter
    -> AssistantRuntimeApp
    -> run_assistant_request
    -> AgentGraphRuntime
```

## Problem

Phase 6A added `GatewayTurnFacade`, but `/agent/run` still calls
`AssistantRuntimeApp` directly. A naive migration would lose fields because
Gateway frames naturally carry `stream.chunk`, `run.end`, trace id, and terminal
status, while HTTP clients expect the full `AgentRunResponse`: `tool_calls`,
`tool_results`, `react_steps`, `decision_trace`, `runtime_info`,
`current_stage`, `blocked_reason`, and normalized errors.

## Chosen Approach

Use an in-process HTTP response capture store.

`/agent/run` creates a unique capture id and includes it in internal Gateway
metadata before calling `GatewayTurnFacade`. The default Gateway backend still
enters `GatewayAgentAdapter` and `AssistantRuntimeApp`; after
`AssistantRuntimeApp.run_request()` returns `AssistantRunArtifacts`, the
Gateway runtime callback stores `artifacts.api_response()` under the capture id.
The HTTP route waits for `run.end`, pops the captured `AgentRunResponse`, and
returns it unchanged.

This keeps rich HTTP response compatibility without putting the complete HTTP
schema into public Gateway `run.end.payload`, and without adding fields to
`RealtimeAgentResult`.

## Request Metadata

Gateway metadata for this phase is internal and prompt-safe:

- `gateway.http_response_capture_id`: generated by the HTTP route, overwritten
  regardless of user metadata.
- `execution_strategy`: copied from `UserRequest.execution_strategy` so the
  realtime adapter can reconstruct the original `UserRequest`.
- existing `request_identity`: preserved from the API identity layer.

Gateway still strips user-supplied `system_prompt_profile`, `channel`, and
`source` metadata before building the backend request.

## Error Handling

- Identity and trial-access failures stay in the HTTP route before Gateway.
- If Gateway returns `run.end` with `reason="error"` and no HTTP response was
  captured, the route raises a sanitized 500 `HTTPException` with the Gateway
  terminal error.
- If Gateway completes but no capture exists, the route raises a sanitized 500
  `HTTPException` with `GATEWAY_HTTP_RESPONSE_MISSING`.
- Captured responses are popped after use so the store does not retain per-run
  user data.

## Out of Scope

- Do not migrate CLI.
- Do not migrate legacy `/ws/agent/{session_id}`.
- Do not change `/agents/run`.
- Do not add observer hooks.
- Do not expose the full HTTP response through Gateway WebSocket frames.

## Testing

- Add a realtime adapter test proving `execution_strategy` is reconstructed
  from Gateway metadata.
- Add an API test proving `/agent/run` enters Gateway by asserting the runtime
  request contains Gateway runtime metadata/history while still returning the
  existing rich `AgentRunResponse`.
- Keep existing identity, trace, session, demo, and product API tests green.

## Stop Point

Stop this phase after HTTP `/agent/run` is Gateway-first and the existing HTTP
response schema remains compatible. The next phase should migrate CLI or legacy
`/ws/agent` one at a time. Observer integration should still wait until Web,
CLI, HTTP, and WebSocket entry paths all converge on Gateway or have explicit
compatibility exceptions.
