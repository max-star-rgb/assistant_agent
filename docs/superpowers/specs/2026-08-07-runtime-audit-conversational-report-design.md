# 运行审计对话式日报设计

## 背景与目标

当前运行审计日报虽然能够区分待处理、代码已修改和真实运行已验证等状态，但最终 Markdown 仍接近正式审计文档：模板标签多、技术附录长、机器标识符密集。维护者阅读后还需要再次让 Codex 转述成自然语言。

本次变更只调整人读日报的表达与信息排序。目标是让日报像 Codex 直接向维护者汇报：先给结论，再说明真正需要处理的事项，最后交代已经修改、只需等待验证的事项。Trace、Score、Git 和测试证据继续留在结构化审计产物中，不削弱内部校验能力。

## 人读日报契约

日报采用对话式表达，正常长度控制在约 500～1000 个中文字。内容顺序如下：

1. 日期标题。
2. 一段直接结论：昨天整体表现、今天是否需要处理，以及最重要的事项。
3. 需要当前处理的问题，按优先级用自然段说明现象、用户影响和建议，不使用“发生了什么”“建议怎么做”“怎么确认”等模板标签。
4. 已有代码修改、等待真实运行验证的问题。明确说明当前不建议继续修改，先观察后续真实运行。
5. 仍无法确定的事项；没有内容时不显示。

空日或没有异常时只输出简短结论，例如“昨天运行正常，没有发现需要你处理的问题”，不制造空章节。

人读 Markdown 中不得出现：

- Trace ID、observation ID、Score ID；
- Git commit SHA、测试文件路径；
- `open`、`code_addressed`、`runtime_verified`、`owning module`、`grounding` 等内部字段或术语；
- 证据附录和机器证据列表。

## 结构化证据与生成流程

现有三层审计结构保持不变。第三层异常证据、Git 变更和历史 issue registry 仍通过 stdin 交给 Codex。Codex 继续输出受 JSON Schema 约束的结构化结果，其中保留机器证据引用和问题生命周期状态。

Python 在结构化结果通过 Pydantic、时间顺序和证据引用校验后，再确定性渲染人读 Markdown。渲染器只消费自然语言摘要和经过校验的问题状态，不把任何证据引用写入 Markdown。这样可以同时保证：

- Markdown 对人自然、简洁；
- JSON 对程序可追踪、可校验；
- 代码已修改不会被误写成真实运行已经恢复；
- 日后仍能依据机器证据连续跟踪同一问题。

## 提示词调整

日审计提示词要求 Codex 像直接回复项目维护者一样写内容：结论先行、使用普通中文、明确优先级，并避免审计公文式转述。Codex 不直接生成 Markdown，也不负责决定标题和章节格式；它只生成结构化的自然语言字段。

提示词继续禁止 Codex 浏览完整 bundle、正常 Trace、网络或外部系统，也禁止修改代码、Langfuse、Memory 和生产状态。

## 安全与失败处理

机器标识符即使被 Codex 意外写入自然语言字段，最终渲染前也必须过滤或拒绝，不能只依赖提示词。结构化输出不合法、证据关系不成立或过滤后核心内容为空时，本次审计应失败并保留上一份成功日报，不能静默生成误导性内容。

## 验证范围

在 `tests/tdd/runtime_audit` 中覆盖以下行为：

- 有待处理、等待验证和不确定问题时，输出顺序和语义正确；
- Markdown 不含 Trace、Score、commit SHA、测试路径和内部状态名；
- 不再生成证据附录或模板化问题标签；
- 空日输出简短自然结论；
- 内部 JSON 仍保留证据引用，既有状态与证据校验不放宽；
- 同一日期的幂等生成和失败保留旧报告行为不变。

## 非目标

- 不改变异常 Trace 的筛选规则；
- 不改变 Langfuse、本地 event 或 Git 证据采集范围；
- 不让 Codex 自动修改代码或外部状态；
- 不改变日报定时器、日期命名和不重复生成策略。
