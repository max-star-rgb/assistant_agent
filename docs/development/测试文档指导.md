# 测试与评估体系设计

> 状态：目标设计。本文用于指导后续建立测试与评估体系，不以当前 `tests/` 目录结构为前提。

## 1. 目标

本项目需要同时解决两类问题：

1. 代码修改后，确定性行为是否仍然正确；
2. 使用真实模型、真实 Provider 和真实服务时，Agent 是否真的具备预期能力。

这两类问题不能混在同一个目录和同一种运行方式中。前者属于自动化测试，后者属于评估（eval）。

## 2. test、pytest 和 eval 的区别

### 2.1 Test

Test 验证明确、稳定、可重复的代码契约，例如：

- 非法 Tool 参数是否被拒绝；
- Tool 是否经过 `ActionValidator -> ToolExecutor -> ToolRegistry -> tool`；
- context message 的顺序是否正确；
- memory 是否按 `user_id` 和 `session_id` 隔离；
- cancel、timeout 和 retry 是否产生预期状态。

Test 应尽量离线、快速、确定性，不依赖真实模型临场发挥，也不依赖外部服务的即时状态。

### 2.2 pytest

pytest 是运行 Python test 的工具，不是一种测试类型。单元测试、集成测试和契约测试都可以由 pytest 执行。

pytest 的结果通常是确定性的 `pass/fail`。默认 pytest 不应调用真实 Provider、付费 API 或真实外部服务。

### 2.3 Eval

Eval 用来判断完整 Agent 在真实或接近真实的环境中“表现得怎么样”，例如：

- LLM 是否自主选择了正确的 Tool；
- Tool 参数是否合理；
- 多 Tool 顺序是否正确；
- 最终回答是否整合了真实结果；
- context、memory 和 policy 是否共同产生了正确行为；
- 同一批案例在不同模型、prompt 或版本上的通过率是否变化。

Eval 允许存在模型随机性、外部依赖、耗时和费用。它除了给出通过/失败，还应保存输入、输出、trace、评分、耗时和成本等证据。

## 3. 总体目录设计

建议将自动化测试与评估彻底分开：

```text
tests/
  unit/                    # 纯函数、model、validator 等窄层测试
  integration/             # 多模块协作，使用 mock/fake/local adapter
  contract/                # 协议、schema、事件和稳定外部契约

evals/
  system/                  # 按系统能力进行真实验证
    common/
    tools/
    context/
    memory/
  cases/                   # 面向用户任务的端到端案例评估
    langfuse/              # Dataset seed、Experiment task 和 evaluator 源码

.data/
  evals/                   # 每次真实运行的本地结果，不提交 Git
```

因此，原文中的“系统模块测试”不应放在 `tests/evals/`，建议命名为 **system eval** 并放在根目录 `evals/system/`。

原因是这些任务明确要求真实 Provider、真实 LLM 决策、真实上下文或真实 Mem0。它们验证的是系统能力，不是适合默认 pytest 的确定性代码回归。

## 4. 系统能力评估

System eval 按能力域组织，每个域使用少量、可解释、可重复运行的场景。它的主要目标是定位某一项系统能力是否真实可用，而不是衡量复杂用户任务的整体质量。

### 4.1 Tool eval

目录：

```text
evals/system/tools/
  cases/                   # 每个 Tool 或 Tool 组合的固定输入
  runner.py                # 通过主 runtime 执行
  assertions.py            # 结构化硬断言
```

Tool eval 必须使用真实 chat Provider 和真实 Tool Provider，并经过完整链路：

```text
受控 UserRequest
  -> AgentGraphRuntime / assistant loop
  -> 真实 LLM 返回 tool call
  -> ActionValidator
  -> ToolExecutor
  -> ToolRegistry
  -> 真实 Tool
  -> ToolResult
  -> 真实 LLM 生成最终回答
```

每个场景至少记录：

- 原始用户请求；
- 本轮暴露给模型的 Tool 列表；
- 模型返回的 tool call；
- Tool 名称和结构化输入；
- validation/confirmation 结果；
- Tool 的结构化结果或错误；
- 最终回答；
- run、trace、provider、model、耗时和 token/cost 信息。

硬断言应围绕结构化行为，例如：

- 是否调用了预期 Tool；
- 是否调用了禁止 Tool；
- 参数是否通过 schema 和安全校验；
- 是否成功取得真实 Provider 结果；
- 最终回答是否引用了 Tool 返回的关键事实。

不要只做“直接调用 Tool 函数”的测试，因为那无法证明 LLM、runtime 和治理链路已经连通。为了快速定位故障，可以额外提供一个 provider smoke，但 smoke 不能替代完整 Tool eval。

### 4.2 Context eval

目录：

```text
evals/system/context/
  cases/
  runner.py
  assertions.py
```

Context eval 验证系统实际组装并发送给模型的某一轮上下文。每个场景应输出不脱敏 compiled context 原文，至少包含：

- system prompt；
- conversation history；
- 当前 user message；
- 本轮 memory recall 或 session memory snapshot；
- Tool catalog、schema 和 policy 信息；
- media 或其他结构化输入；
- token 统计、预算、截断或摘要结果。

需要同时做两类判断：

1. **结构正确性**：角色、顺序、Tool schema、memory 注入位置、token accounting 等是否正确；
2. **内容质量**：上下文是否缺失必要信息、包含冲突指令、重复内容、无关记忆或过量 Tool。

这里的“真实上下文”是指真实 runtime 编译并提交给真实 Provider 的上下文，不是从生产环境复制真实用户对话。

### 4.3 Memory eval

目录：

```text
evals/system/memory/
  cases/
  runner.py
  cleanup.py
```

Memory eval 的目标是在真实 Mem0 或真实外部 memory service 上覆盖：

- 新增记忆；
- 搜索和读取记忆；
- 更新记忆；
- 删除记忆；
- 用户与 session 身份隔离；
- session 启动时的召回；
- turn 中 memory snapshot 的复用；
- 对话结束或策略触发后的记忆写入；
- memory 服务失败时 runtime 的可解释行为。

每次运行必须使用独立的测试 namespace 或唯一用户标识，并在结束后执行清理。清理失败要进入运行报告，
不能静默遗留测试数据。当前项目公开契约只有 capture/recall，没有 update/delete/reset，因此暂不提供
会写入真实 Mem0 的自动 runner；必须先补齐受治理的清理契约，再落地上述完整闭环。

Runtime system eval 暂不建立独立目录。provider streaming、multi-turn、cancel、interrupt、timeout、
retry 和事件完整性先由确定性 pytest 保护；以后出现必须依赖真实模型或真实环境才能回答的问题时，
再新增 `evals/system/runtime/`。

## 5. 案例评估

System eval 回答“某项能力是否连通”，case eval 回答“Agent 能否完成真实用户任务”。

建议目录：

```text
evals/cases/
  langfuse/
    agent_closed_loop_v1.seed.json
    experiment.py
    agent_strict_pass.ts
    local_runner.py
```

### 5.1 案例分层

- `simple`：单一目标、单 Tool 或明确不应调用 Tool；
- `medium`：两步任务、两类信息源、个性化上下文或确认边界；
- `advanced`：多 Tool 协作、顺序依赖、约束权衡、失败恢复或事实不确定性处理。

案例不应通过“用户直接说出 Tool 名称”机械触发能力，而应描述真实任务，让 LLM 自主判断是否调用 Tool。

### 5.2 案例数据

每个案例建议包含：

- `id`、版本、能力标签和难度；
- 用户输入和受控环境初始状态；
- memory、media、时间等前置条件；
- 至少应调用的 Tool；
- 禁止调用的 Tool；
- 有数据依赖时的 Tool 顺序；
- 最小/最大调用次数；
- 是否需要 confirmation；
- 预期环境状态变化；
- 最终回答必须包含的稳定事实；
- 评分规则和权重。

不要把完整自然语言答案作为唯一标准答案。更稳定的方式是评分结构化行为、必要事实、policy 合规和状态变化。

### 5.3 Langfuse 的职责

已有 Langfuse 评估体系可以作为 case eval 的运行平台：

```text
Versioned Dataset
  -> Experiment
  -> Agent Runtime
  -> Trace 与结构化执行证据
  -> Evaluator
  -> Score
  -> 不同模型/prompt/版本的对比
```

## 6. 统一运行与结果协议

### 6.1 显式启用真实运行

所有 system eval 和真实 case eval 必须显式启用 real 模式。仅检测到 API key 不能自动发起调用，也不能从 real 静默回退到 mock。

运行前先执行 preflight：

- provider mode 是否为 `real`；
- chat Provider 是否完整配置；
- 案例需要的 Tool Provider 是否完整配置；
- 外部服务是否可达；
- 写入型场景是否具备确认和清理策略；
- 预计案例数、最大耗时和费用是否在本次预算内。

缺少必需配置时应在调用前终止，并报告具体缺项。

### 6.2 统一状态

每个 eval case 建议使用以下终态：

- `passed`：硬断言通过；
- `failed`：Agent 行为或结果不满足预期；
- `error`：Provider、网络、runner 或评估器异常；
- `blocked`：运行前置条件不满足，未真正执行。

不能用 `skip` 或 mock fallback 把未验证的真实能力展示成通过。

### 6.3 统一 artifact

每次运行写入：

```text
.data/evals/<run_id>/
  manifest.json            # 代码版本、配置摘要、provider/model、案例集版本
  summary.json             # 总数、通过率、错误率、耗时和成本
  cases/
    <case_id>.json         # 输入、结构化证据、断言、评分和错误
  traces/                  # 可选的脱敏 trace
```

终端只打印摘要和失败定位。完整 Tool 输入/结果、compiled context 和 trace 放入 artifact，并进行脱敏和大小限制。

### 6.4 可复现性

每次报告至少记录：

- Git commit 或工作区版本标识；
- dataset 和 evaluator 版本；
- provider、model、temperature、seed（若支持）；
- prompt/config 版本；
- 时间、重试次数、超时；
- Tool/MCP 配置摘要；
- 每项延迟和成本。

真实模型存在随机性。关键 case 可以重复运行多次，报告通过率和波动，而不是把一次偶然结果当作稳定结论。

## 7. 安全与数据要求

- 不提交 API key、token、真实 `.env` 或 Provider 原始响应；
- 不使用真实用户对话、记忆、联系人、日历或媒体作为固定案例；
- 所有案例使用受控测试身份和合成数据；
- 输出 context、Tool 参数和 trace 前必须脱敏；
- 写入型 Tool 必须有明确的测试目标、独立 namespace、confirmation 和清理步骤；
- 危险或高费用能力默认不运行，必须单独显式选择；
- `.data/evals/` 不进入版本控制；
- 最终报告要说明是否调用了真实 Provider、调用范围、失败项和未清理数据。

## 8. 建议补充的内容

在原草案的 Tool、context、memory 和 Langfuse 案例之外，还应补充以下能力：

1. **Runtime 主链路**：multi-turn、stream、cancel、interrupt、timeout、retry 和 Tool 失败恢复；
2. **统一证据模型**：不同 eval 输出同一结构，便于本地报告和 Langfuse 复用；
3. **数据集版本管理**：案例、evaluator 和 prompt 变更必须可追踪；
4. **错误分类**：区分代码缺陷、外部集成异常和模型质量问题；
5. **成本与耗时预算**：真实 eval 在执行前给出上限，运行后记录实际值；
6. **重复运行策略**：关键模型行为用多次运行统计稳定性；
7. **基线对比**：新模型、新 prompt 或新 runtime 与已知基线做同一数据集对比；
8. **人工复核队列**：规则与自动评分冲突、危险操作或低置信度案例进入人工复核；
9. **CI 边界**：CI 默认只跑 `tests/`；system eval 和真实 case eval 由人工、受控任务或显式流水线触发；
10. **失败最小化**：失败案例应能缩减成最小输入，并沉淀为确定性 regression test 或稳定 eval case。

## 9. 建设顺序

建议按以下顺序落地：

1. 定义统一 `EvalCase`、`EvalResult`、artifact 和 preflight 协议；
2. 先完成一个真实 Tool eval，打通 LLM、runtime、治理链路、真实 Tool 和结果落盘；
3. 增加 context artifact 与结构化断言；
4. 增加真实 Mem0 生命周期和清理验证；
5. 将现有 Langfuse 案例整理到 versioned dataset；
6. 建立分项 evaluator、基线和对比报告；
7. 最后补充 runtime、多轮和失败恢复场景。

第一阶段不追求案例数量，先确保一个案例能够提供完整、可信、可定位的证据，再扩展覆盖面。
